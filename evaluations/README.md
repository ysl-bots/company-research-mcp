# KOSPI 상위 30개사 DART 평가

모집단과 대상 공시의 목록을 고정한 후 접수번호별 원문을 수집한다.

    uv run python -m evaluations.capture 접수번호

DART_API_KEY는 환경변수로 전달한다. 두 평가 단계는 같은 접수번호와 SHA-256으로 식별한 ZIP을 읽는다. 원문은 data/에 로컬 보관한다.

## 평가 절차

1. 기업과 공시별로 수집 계획 버전, 원문 위치, 실제 수집 산출물, MCP 요청과 응답을 연결한다.
2. 정적 검사에서 계획의 필수 항목, 수집 코드의 항목 매핑, 산출물의 존재와 원문 일치를 확인한다.
3. Judge는 같은 사례의 원문 구절을 인용해 의미상 누락과 왜곡을 판정한다. 원문에 있고 계획에 없는 내용은 합의한 요구사항이 있을 때만 계획 결함으로 분류한다. 수집 산출물이 정상이면 MCP 응답 생성 경로를 별도로 확인한다. 증거가 부족하면 원인 미확정으로 기록한다.

사례 데이터와 채점기를 분리하는 구조는 [OpenAI Evals](https://github.com/openai/evals)를 참고했다. Judge의 장문 선호 편향과 사람 판정과의 일치도를 검토하는 근거는 [Judging LLM-as-a-Judge](https://arxiv.org/abs/2306.05685)다. 실행 시 모델 버전, 채점 척도와 프롬프트를 기록한다.

## 1차 평가 범위

2026-11-26 종가 기준 KOSPI 보통주 시가총액 상위 30개사를 대상으로 한다. 우선주 시가총액은 합산하지 않는다. 기준일 현재 공개된 기업별 최신 사업보고서 1건과 해당 사업연도의 get_dart_filings 응답을 비교한다. 순위 원자료, 종목코드, DART 고유번호, 접수번호를 고정한 뒤 원문을 받는다.

## 합의한 공통 필수 항목

1. 주력 사업·제품과 부문별 매출 구성
2. 시장 여건과 경쟁 요소
3. 연구개발과 투자 방향
4. 최근 3개년 매출과 영업이익

각 항목은 해당 기업이 공시한 범위에서 평가한다. 원문 표·문단을 식별하고 수치의 기간·단위·연결 또는 별도 기준을 보존한다. 미공시와 수집 누락은 구분한다. 부채비율과 영업활동 현금흐름은 선택 항목이며 공통 필수 충족률에서 제외한다.

## 합의한 취업 활용성 기준

- 기업 고유성. 응답에서 뽑은 핵심 소재에 기업명만 바꿔 넣어도 설명이 성립하는지 검토한다. 제품명이나 고유명사의 등장만으로 판단하지 않고, 어떤 사업·기술·시장 여건이 그 회사에 중요한지 원문 근거를 확인한다.
- 개인 경험과의 접점. 동일한 기업 근거에 지원자의 경험을 함께 제공했을 때, 경험에서 실제로 한 일과 기업의 구체적 과제 사이에서 가장 적합한 접점을 골라 설명하는지 평가한다. 판정 근거는 기업 원문과 경험 입력 양쪽에서 찾는다.

MCP는 근거를 반환하고 호스트 모델이 활용 답변을 작성한다. 동일 기업·경험·질문·호스트 모델을 고정한 쌍으로 답변을 생성한다. 한 답변에는 get_dart_filings 응답의 근거를, 다른 답변에는 같은 접수번호의 DART 원문에서 독립적으로 확인한 근거를 제공한다. 두 답변 모두 기업 고유성과 경험 접점을 평가한다. 점수 차이만으로 원인을 확정하지 않고 실제 제공된 근거와 답변을 대조한다.

경험 사례는 공통 비교용 가상 경험과 실제 활용성 확인용 익명화 경험을 함께 사용한다. 사례마다 지원자가 수행한 행동과 판단, 결과를 기록하며 동일 쌍에는 같은 경험 입력을 사용한다. IT 직무를 우선한다. 독립 추출기는 MCP 응답을 보기 전에 같은 질문·경험을 바탕으로 30개사의 DART 원문에서 근거 후보를 선정하고 표·문단 위치를 기록한다. 사람은 그중 표본을 검수한다. 30개사 중 업종 다양성을 고려해 6개사(20%)를 표본으로 뽑는다. 검수자는 인용 정확성과 더 적합한 소재의 누락 여부를 확인하고, 반복 오류가 발견되면 같은 추출 규칙을 적용한 기업까지 재검토한다.

공통 가상 경험은 프론트엔드, 백엔드·플랫폼, 데이터 엔지니어링 각 1건이다. 같은 세 경험을 30개사 모두에 적용해 90쌍의 답변을 비교한다. 익명화 실경험을 적용하는 사례는 별도로 집계한다.

## 공통 경험 입력

| 직무 | 가상 지원자가 수행한 일 |
|---|---|
| 프론트엔드 | 신청 화면 이탈 구간을 분석하고 키보드 사용자가 오류 입력란을 찾기 어려운 현상을 재현했다. 오류 안내와 포커스 이동을 개선한 뒤 완료율 변화를 확인했다. |
| 백엔드·플랫폼 | 주문 처리 지연을 추적해 외부 서비스 타임아웃 이후 재시도가 몰리는 현상을 발견했다. 재시도 정책과 중복 처리 방지를 적용하고 부하 테스트로 검증했다. |
| 데이터 엔지니어링 | 대시보드와 정산 보고서의 매출 차이를 추적해 취소 거래 반영 시점의 차이를 발견했다. 집계 기준을 통일하고 오류 탐지 규칙을 추가했다. |

공시 근거가 약할 때 그 한계를 명시한 답변을 인정한다. 공시에 없는 사내 시스템이나 장애를 사실로 제시하면 감점한다.

## 실행 순서

수집 범위는 update/dart-coverage 브랜치의 점검표로 먼저 확인한다. 필수 범위의 누락을 보완한 뒤 평가할 수집 버전과 MCP 응답을 고정하고 정적 검사, LLM 평가 순서로 진행한다. 판정마다 회사·접수번호·경험·근거 위치와 판정 이유를 남긴다.
